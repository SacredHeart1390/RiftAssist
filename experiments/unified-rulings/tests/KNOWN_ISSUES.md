# 회귀 테스트에서 발견한 기존 문제

## UI-001 초기 서버 연결 실패 안내 누락 — 로컬 소스 수정 완료

- 위치: `releases/v0.1.7/public/app-ui5.js`의 최초 `/api/health` 조회.
- 기존 동작: 네트워크 실패를 빈 catch로 무시해 연결 확인 문구와 비활성 버튼이 계속 남았다.
- 재현: E2E04에서 브라우저의 최초 상태 조회를 끊으면 실패 안내가 나타나지 않아 테스트 실패.
- 수정: 기존 안내 영역의 한국어/영어 실패·새로고침 메시지, 실패 상태 보존,10초 상태 조회 제한. 새 UI 기능은 추가하지 않음. 서비스 워커 캐시 이름 갱신.
- 확인: E2E04의 실패 표시→새로고침→질문/답변 회복 통과. 전체 E2E5/5·기존 회귀11/11 통과. 운영 프로세스 재시작/외부 배포 없음.

## RULE-001 정상적인 금지 판정을 근거 부족으로 오인 — 로컬 소스 수정 완료

- 위치: `releases/v0.1.7/src/answer-quality.js`, `recoveryRequest()`의 `gap` 정규식 및 `unresolved-ruling` 분기.
- 재현: `evidenceAssessment.status='complete'`, 유효한 인용355.15/359.3.e.5와 처리 순서가 있는 답변의 결론을 **‘유성의 대상을 다시 확정할 수 없습니다. 후퇴 후 남은 유닛에만 피해3을 입힙니다.’**로 설정한다.
- 기대: 대상 변경이 금지된다는 확정적 판정이므로 재검색 요청 없음(null).
- 실제: `확정…없`이 근거 부족 정규식에 걸려 `{reason:'unresolved-ruling', ...}`를 반환한다. complete 평가여도 이 정규식 검사를 거친다.
- 근거: 현재 공식355.15는 지시가 없는 한 이미 한 선택을 바꿀 수 없다고 명시하고,359.3.e.5는 부적법한 대상에 관한 지시를 수행할 수 없다고 명시한다. 이 결론 자체는 불확실성 표시가 아니다.
- 영향: 정상 답변에도 불필요한 두 번째 생성이 발생할 수 있다. 두 번째 답변도 같은 표현이면 기존 서버 복구 경로에서 `retrieval-error`가 될 수 있다. 추가 토큰 사용과 정상 판정 미표시 가능성이 있다.
- 회귀 테스트:10번으로 기존 실패를 재현한 뒤, 한국어 불확실성 정규식을 판정·결론·시점·시기·순서·여부를 확정할 수 없다는 문맥으로 좁혔다. 명시적인 missing-rule/source-conflict 및 다른 검사 분기는 유지했다. 실제 처리 순서 미확정 표현은 계속 감지하는11번도 추가했다.
- CI 준비 후 최종 실행:11개 모두 통과. 운영 프로세스 재시작·서버 실행·배포는 수행하지 않았으므로 현재 실행 중인 앱에 적용됐다는 뜻은 아니다.

## 테스트 작성 중 수정한 문제

03번의 최초 실패는 테스트가 카드 본문을 전체 요청의 중첩 이스케이프 문자열과 비교해서 발생했다. 실제 전송 JSON의 카드 배열을 파싱해 본문을 비교하도록 테스트를 수정했고, 최종 실행에서 통과했다. 앱의 카드 전달 버그로 분류하지 않는다.
