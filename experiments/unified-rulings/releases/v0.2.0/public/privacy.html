1. 처리 목적과 항목

RiftAssist는 카드 검색, 규칙 참고 답변, 근거 번역, 오류 제보 처리 및 남용·중복 요청 방지를 위해 다음 정보를 처리합니다. 질문이나 제보에 실명, 연락처, 계정 정보, 타인의 개인정보 또는 비밀을 적지 마세요.

  • 질문: 입력한 질문, 언어, 선택·자동 인식 카드, 요청 번호·중복 확인용 값, AI 답변과 참조 근거, 처리 상태·시각·소요 시간, 검색·보강 기록, 자료·모델 버전, 토큰 사용량·오류 코드 및 공급자 응답 식별자.
  • 오류 제보: 분류, 설명, 기대 답변, 태그, 언어, 접수·변경 시각과 상태, 관리자 메모. 질문을 연결하면 그 시점의 질문·답변·근거·처리 기록 사본도 저장합니다.
  • 세션: 무작위 쿠키 식별자의 SHA-256 해시로 요청·제보·사용 한도를 연결합니다. 신규 세션 수는 날짜별로 집계합니다. 이름·이메일·Riot 계정 가입 기능은 현재 앱에 없습니다. 세션 식별자가 있으므로 완전한 익명 처리라고 표현하지 않습니다.
  • 카드 검색어와 입력 중 카드 인식 요청은 앱 서버로 전송됩니다. 해당 API에 검색 본문을 별도로 영구 저장하는 코드는 확인되지 않았습니다. 사진 첨부는 서버에서도 거절하며 현재 질문 기능은 텍스트 전용입니다.

2. 외부 전송

카드 자동 갱신 개발 기능은 현재 합성 스냅샷만 수집합니다. 개발 루트에 원문·번역 후보·변경 전후·출처·수집/공개 시각·누락 상태·검토 참조와 갱신 시도/실패 코드를 보관하며 자동 만료하지 않습니다. 사용자 질문·운영 DB·키를 입력으로 사용하지 않습니다. 실제 공식 수집/번역 제공자 연결 전 저장 용량·접근·보관·파기, 검토 참조에 개인정보를 넣지 않는 절차를 확인해야 합니다.

v0.2.0의 카드 한국어 번역 후보 생성기는 현재 합성 카드와 모의 응답만 사용하며 실제 번역 공급자를 호출하지 않습니다. 향후 별도 구현·활성화할 공급자 어댑터에는 허용된 영어 카드와 용어집·공식 예제만 전달하도록 설계되어 있고 사용자 질문을 사용하지 않습니다. 개발 루트에 원문·번역 후보·모델·시각·검토 참조·캐시를 별도로 보관하며 자동 만료하지 않습니다. 실제 연결 전 공급자·전송 항목·처리 국가·보관·계약 조건과 필요한 고지·동의, 검토 참조의 개인정보 포함 여부를 확인하고 이 방침을 보완해야 합니다.

권한 확인 규칙 전용 모드: approved-rules-only에서는 카드·저지 사례를 포함하지 않으며 RiftJudge 외부 검색과 원문 번역 API를 차단합니다. 이 모드에서 별도 승인 후 AI 생성을 활성화하면 사용자 질문·언어와 허용된 규칙 근거가 OpenAI로 전송됩니다. 아래 사례 검색·원문 번역 설명은 해당 기능이 허용된 다른 모드에 한정됩니다.

  • OpenAI API: AI 생성이 켜져 있고 근거·한도 조건을 충족하면 질문, 언어, 선택 카드 정보·영문 본문, 검색된 규칙·RiftJudge 사례와 관련 자료 문맥을 HTTPS로 전송합니다. 근거 부족 시 보강 생성이 한 번 더 실행될 수 있습니다. 근거 번역 요청에는 등록된 출처 원문과 카드 이름·용어집을 전송하며 사용자 질문 전체를 번역 입력에 넣지는 않습니다. 호출은 store: false로 설정되어 있습니다. 이 설정을 공급자의 모든 로그·보관이 없다는 보장으로 해석하지 않습니다. 공급자 계약, 실제 보관 조건·처리 국가와 국외 이전 요건은 운영자 확인이 필요합니다.
  • RiftJudge: 로컬 사례 검색만으로 충분하지 않을 때 app.riftjudge.com의 검색 API로 질문에서 만든 검색어, 질문 일부 및 카드 이름을 전송합니다. 각 검색어는 최대 500자입니다. OpenAI 생성을 끈 경우에도 외부 사례 검색은 실행될 수 있습니다. 이 외부 서비스의 보관·처리 조건은 확인이 필요합니다.
  • 카드 제한과 이미지 제공처: 서버의 기본 정책은 카드 공개 표시·이미지·카탈로그의 AI 입력을 제한합니다. 권한 미확인 카드 본문·번역·이미지·카드명 용어집을 API로 제공하거나 AI 입력에 추가하지 않습니다. 해당 카드를 인식한 질문은 AI 답변을 보류하고 규칙·저지 사례를 검색합니다. 이때 사용자가 직접 입력한 질문 일부는 RiftJudge 검색에 전송될 수 있습니다. 운영자가 앱 승인·이용 범위를 확인해 검증 카드 모드를 활성화하고 카드별 권한 조건도 충족한 경우에만 해당 카드를 표시합니다. 그 경우 브라우저가 외부 이미지 주소에서 직접 불러오며, 제공처는 접속 IP 등 통신 정보를 받을 수 있습니다. 보존된 미확인 자료에는 cmsassets.rgpub.io와 media.riftnaru.com 주소가 있으나 기본 정책으로는 표시하지 않습니다. 이미지 요소는 no-referrer를 사용합니다. 이미 열려 있던 화면·브라우저 메모리·이전 외부 전송까지 소급 취소되는 것은 아닙니다.

3. 저장·암호화와 접근

카드 관리자 검토 개발 기능은 별도 개발 루트의 평문 JSON 감사 이력에 설정된 관리자 식별자, 승인·거절·보류 사유와 시각, 후보/항목 해시, 경고 확인, 승인본 구성·최종 활성화·롤백 의도와 결과를 저장합니다. 서명 키는 전용 파이프로 메모리에 공급하며 감사 이력에 기록하지 않습니다. 사용자 질문·운영 DB·기존 운영 키를 사용하지 않습니다. 검토 이력은 자동 만료하지 않으므로 사유에 개인정보·비밀을 넣지 않는 절차, 실제 관리자 신원 연동, 접근 권한·보관·삭제·암호화/백업 정책을 운영자가 확정해야 합니다.

운영 자료 폴더의 SQLite에 질문·응답·검색 처리 기록, 제보 내용·연결 사본·관리자 메모와 이벤트 내용을 AES-256-GCM으로 암호화해 저장합니다. 세션 소유자 해시, 요청·제보 번호, 시각, 상태, 분류, 중복 확인용 해시, 호출·토큰 집계 등 메타데이터는 DB 전체 암호화의 대상이 아닙니다. 암호화 키는 같은 서버의 별도 파일에 있으며, 서버와 키를 관리하는 운영자는 복호화할 수 있습니다. 종단간 암호화가 아닙니다.

제보 목록은 해당 세션에 한정되고, 관리자 기능에는 별도 로컬 인증이 적용됩니다. 관리자는 제보 내용, 연결된 질문·답변 사본과 이력을 열람하고 상태·메모를 변경할 수 있습니다. 실제 접근 권한·키 보관·인프라 보안 설정은 별도 운영 확인이 필요합니다.

4. 보관과 삭제

  • 질문 생성 후 7일이 지나면 질문·응답 본문을 비우고, 30일이 지나면 요청 행과 검색·처리 기록을 삭제 대상으로 처리합니다. 검색 보강어·모델 평가에 질문에서 파생된 문구가 포함되면 그 문구는 처리 기록에 30일까지 남을 수 있습니다.
  • 호출 기록·이벤트는 생성 후 30일, 신규 세션 집계는 날짜 기준 30일 후 정리 대상입니다.
  • 제보는 최초 접수 후 90일이 지나면 연결 사본과 상태 이력·메모를 함께 삭제 대상으로 처리합니다. 제보에 복사된 질문·답변은 원본 질문의 7일 정리와 별개로 남습니다. 상태 변경으로 접수일이 갱신되지는 않습니다.
  • 정리 작업은 서버 시작 시와 실행 중 약 1시간마다 수행됩니다. 서버 중단·작업 실패로 실제 삭제가 늦어질 수 있습니다. SQLite의 secure_delete 및 WAL 체크포인트를 사용하지만 저장장치·WAL·외부 사본까지 즉시 완전 소거한다고 보장하지 않습니다.
  • 관리자 백업에는 DB와 복호화 키가 함께 포함됩니다. 백업 자동 만료·연쇄 삭제 기능은 없으며, 백업 사본은 운영자가 별도로 보관·삭제해야 합니다. 실제 백업 주기·기간·삭제 절차는 확인이 필요합니다.
  • 공개 규칙·커뮤니티 사례는 지식 릴리스 JSON, 번역 캐시 JSON 및 출처 수집용 SQLite에 별도로 보관됩니다. 출처 수집 DB에는 공개 자료·동기화/재시도 상태가 평문으로 저장되며 사용자 운영 DB의 콘텐츠 암호화 대상이 아닙니다. 공개 자료에도 작성자 식별정보 등이 포함될 가능성이 있어 운영 검토가 필요합니다. 사용자 질문을 번역 원문으로 사용하지 않으며 이 자료들에 자동 보관 만료는 없습니다.

별도 승인된 수동 교체 백업은 DB·관련 키·서비스 설정과, 존재하고 처리 승인된 경우의 .env를 서버 내 AES-GCM 봉인 파일로 보관합니다. 복구용 wrapping key는 별도 private 파일이며 운영 접근자가 둘 다 확보하면 복호화할 수 있습니다. 백업·키·사용자 기록을 GitHub/CI 아티팩트나 외부 AI로 자동 전송하지 않습니다. 자동 만료는 없으며 실제 보관·삭제와 오프호스트 복구 정책은 운영자가 확정해야 합니다.

5. 쿠키·브라우저 저장소·로그

rift_session_v020 쿠키는 서명된 무작위 세션으로 30일간 유효하며 HttpOnly, SameSite=Strict, Path=/를 사용합니다. 공개 HTTPS 호스트에서는 Secure도 적용합니다. 검증된 운영 업데이트에서는 같은 세션 키로 서명을 확인한 기존 rift_session을 연결하여 제보 소유자를 유지할 수 있습니다. 이때 원래 발급 시점의 만료 기한은 늘리지 않고 이전 쿠키도 자동 삭제하지 않습니다. 개발 환경에서는 기본적으로 버전별 세션을 분리합니다. 쿠키를 지우면 같은 브라우저에서 기존 제보를 조회하는 연결이 사라질 수 있으며 서버 기록이 즉시 삭제되는 것은 아닙니다.

언어 선택은 localStorage의 riftbound-language에, 최근 카드 ID는 탭의 sessionStorage의 riftassi-card-ids에 저장합니다. 언어 설정은 사용자가 지울 때까지, 카드 ID는 탭 세션 동안 유지될 수 있습니다. 서비스 워커는 화면·스크립트 같은 정적 파일을 Cache Storage에 저장하고 API 요청은 캐시하지 않습니다. 브라우저 사이트 데이터 삭제로 제거할 수 있습니다. 현재 화면 코드에는 광고·분석용 추적기를 확인하지 못했습니다.

앱은 질문·답변 본문을 JSONL 로그에 기록하지 않습니다. 표준 출력·오류에는 시작·상태, 요청 식별자, 오류 코드 등이 나올 수 있고 작업 서버 로그 파일로 남을 수 있습니다. 호스팅·터널·프록시가 IP, URL, 접속 시각 등을 기록하는지와 그 보관 기간은 앱 코드만으로 확인할 수 없습니다.

6. 문의·열람·삭제 요청

개인정보처리자의 신원·연락처와 열람·정정·삭제 등 권리 행사 창구는 공개 전에 확정해야 합니다. 현재 앱에는 개인정보 삭제 전용 API나 자동 삭제 요청 화면이 없습니다. 오류 제보 기능이 법정 권리 요청 창구를 대신한다고 가정하지 않습니다. 요청 처리·본인 확인·백업 삭제 절차도 운영자 확인이 필요합니다.

1. Purpose and data

RiftAssist processes questions, language, selected or recognized cards, request and deduplication identifiers, generated answers, sources, search/recovery traces, timestamps, status, duration, model/source versions, usage, errors and provider response IDs to provide reference answers and prevent abuse. Reports contain category, description, expected answer, tags, language, timestamps, status and administrator notes. Linking a question copies its question, answer, sources and trace into the report.

A SHA-256 hash of a random session identifier links requests, reports and usage limits; new sessions are counted by date. This is not complete anonymity. There is no name/email/Riot account registration in the current app. Card searches and text used for card recognition reach the server; no separate persistent search-body storage was found in those APIs. Image attachments are rejected by the server. Do not enter personal, account or confidential information about yourself or others.

2. External services

Reviewed rules-only mode: approved-rules-only includes no cards or judge cases and blocks external RiftJudge search and source-translation requests. If AI generation is separately approved and enabled, the question, language and permitted rule evidence are sent to OpenAI. The case-search and source-translation descriptions below apply to other modes where those features are permitted.

The card-sync development feature currently collects synthetic snapshots only. Source/translation candidates, before/after changes, provenance, collection/publication times, missing-card observations, review references and attempt/failure codes are retained in the isolated development root without automatic expiry. User questions, production databases and keys are not inputs. Before connecting real collectors/providers, confirm capacity, access, retention/deletion and procedures to keep personal information out of review references.

The v0.2.0 Korean-card candidate generator currently uses synthetic cards and mock responses only. A future separately implemented and enabled provider adapter is designed to receive permitted English cards, glossary terms and official examples, without user questions. Source text, candidate translations, model/time/review metadata and cache records are retained separately in the development root without automatic expiry. Before connecting a real provider, verify the provider, transmitted fields, processing countries, retention, contracts, required disclosure/consent and personal information in review references, and update this policy.

OpenAI: When generation is enabled and evidence/limit checks pass, questions, language, selected card information and English text, retrieved rules and RiftJudge cases, and source context are sent over HTTPS. 3. Storage and access

The card-review development feature retains configured administrator identifiers, approve/reject/hold reasons and times, candidate/item hashes, warning acknowledgements, staged packages and final activation/rollback intents and outcomes in separate plaintext JSON audit records in the development root. Signing credentials enter memory through a private pipe and are not written to the audit journal. User questions, production databases and existing production keys are not used. These records do not expire automatically. The operator must confirm actual administrator identity mapping, access, retention/deletion, encryption/backups and procedures to keep personal information and secrets out of review reasons.

Question/response/trace content, report content and snapshots, administrator notes and events are encrypted using AES-256-GCM in SQLite. Session-owner hashes, IDs, timestamps, status, categories, deduplication hashes and usage metadata are not covered by whole-database encryption. The encryption key is a separate file on the same server. Operators controlling both can decrypt content; this is not end-to-end encryption. Report lists are session-scoped. A separately authenticated local administrator can view report content, linked snapshots and history and update status/notes. Actual access controls, key handling and infrastructure security require operational confirmation.

4. Retention and cleanup

  • Question and response bodies become eligible to be cleared 7 days after question creation. Request rows and traces become eligible for deletion after 30 days. Recovery queries/model assessments can retain phrases derived from the question in traces until the 30-day cleanup.
  • Calls and events become eligible after 30 days; new-session aggregates are cleaned by date after 30 days.
  • Reports, linked question/answer copies and history/notes become eligible 90 days after initial receipt, independently of the question’s 7-day cleanup. Status updates do not reset that receipt date.
  • Cleanup runs at startup and roughly hourly while running. Downtime or failures may delay deletion. SQLite uses secure_delete and WAL checkpoints; immediate erasure from storage media, WAL files and external copies is not guaranteed.
  • Administrator backups include both the DB and its decryption key. There is no automatic backup expiry or cascading deletion of backup copies. Operators must confirm and manage backup frequency, retention and deletion separately.
  • Public rules/cases are retained in knowledge-release JSON, translation-cache JSON and a separate source-collection SQLite database. Source documents and synchronization/retry state are plaintext there, outside user operational-content encryption. Public source material may contain author identifiers and requires review. User questions are not translation source text; these stores have no automatic expiry.

Separately approved manual replacement backups seal the DB, related keys, service configuration and, when present and explicitly approved for processing, .env in a server-local AES-GCM archive. Its wrapping key is a separate private file; an operator controlling both can decrypt it. Backups, keys and user records are not automatically sent to GitHub/CI artifacts or external AI. These copies do not expire automatically; actual retention, deletion and off-host recovery policies require operator confirmation.

5. Cookies, browser storage and logs

The signed random rift_session_v020 cookie is valid for 30 days with HttpOnly, SameSite=Strict and Path=/; public HTTPS hosts also use Secure. A verified production update can link an existing rift_session after validating its signature with the preserved session key. The original expiry is retained and the older cookie is not automatically deleted. Development sessions remain separate by default. Clearing cookies can break access to existing reports without immediately deleting server records. Language preference uses localStorage key riftbound-language until cleared; recent card IDs use the tab’s sessionStorage key riftassi-card-ids for the tab session. The service worker caches static UI files, excluding API requests. Browser site-data controls can clear these stores. No advertising or analytics tracker was found in the current screen code.

The app does not write question/answer bodies to JSONL logs. Startup/status output, request IDs and error codes can appear in stdout/stderr and worker log files. Infrastructure, proxy or tunnel collection of IP addresses, URLs and access times, and their retention periods, cannot be established from application code.
