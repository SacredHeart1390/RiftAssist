# Control Center 3차 — 간단한 확인과 Azure 상태 대시보드

2026-11-02 후속: [SSH 조회 오류 분석·수정](SSH-TROUBLESHOOTING.md). 기존 3차 기능을 유지하며 원격 명령 실패/파이프 오류의 잘못된 단절 분류를 수정합니다.

2026-10-31 · v0.2.0 · `feature/riot-api-v0.2` · Draft PR #1

Windows 10 22H2 x64용 WPF 앱의 기존 2차 기능을 유지하며 확인창과 상태 표시를 정리했다. 실제 Azure 조회는 이번 개발/CI에서 실행하지 않는다. 운영 서비스 제어·관리자 데이터 접근·DB 복원·운영 배포는 계속 비활성이다.

## 확인 절차

| 작업 | 3차 UI |
| --- | --- |
| 시작/중지/재시작, AI·호출 한도·hosting 설정, 제보 상태, 로컬 SSH 설정 저장 | ‘정말 실행하시겠습니까?’ → 예/아니요 |
| 카드/번역 승인·거절·보류, 승인 후보 구성 | 같은 간단한 확인. 카드 승인 경고는 확인창에 표시 |
| 조회/새로고침/상세/감사/설정 불러오기 | 확인창 없음 |
| Azure SSH 상태 조회 | 사용자가 버튼을 누를 때 1회 실행. 체크박스·사유·문구 입력 없음 |
| DB/복호화 키 포함 개발 백업, 개발 앱 버전 적용, 자료 최종 활성화/롤백·복구 | 확인 항목·정확한 확인 문구 유지. 사유는 자동 생성 |
| 영구 삭제·운영 DB 복원·운영 배포 | 기능을 추가하거나 활성화하지 않음. 미등록 작업은 보호 대상으로 분류 |

일반 확인창에는 체크박스나 입력칸이 없다. Enter의 기본 선택은 ‘아니요’이며 취소 시 요청을 보내지 않는다. 제보의 선택적 처리 메모는 그대로 쓰고, 취소/실패하면 메모를 지우지 않는다. 작업 사유를 별도로 입력하지 않는다.

`UserInteraction.AuditReason`이 고정 작업명과 개발 GUID/제보 ID/상태/버전 같은 대상 식별자로 사유를 만든다. 제보 본문·메모·SSH 키/계정/주소/경로를 자동 사유에 복사하지 않는다. 기존 Node 인증·역할·서명/HMAC·nonce·중복 작업 ID·revision/fingerprint·경고 확인·감사 journal과 잠금은 유지한다. 내부 API는 여전히 비어 있는 사유·미확인 변경·미승인 경고·Azure 운영 요청을 거절한다. UI에서 예를 선택한 경우에만 생성한 사유와 확인 결과를 전달한다.

카드 승인 시 표시한 경고를 확인한 예 선택으로 기존 경고 acknowledgement를 전달한다. 차단 오류는 여전히 승인할 수 없으며, 후보 구성은 활성화하지 않는다. 최종 포인터 전환은 별도 권한·해시/버전·보호 확인을 유지한다.

## 대시보드와 설정

CPU, RAM, 디스크, 가동시간, 웹사이트/앱 HTTP, systemd를 개별 카드로 표시한다. HTTP 무응답/오류와 실패·중지한 서비스를 ‘정상’으로 표시하지 않는다. 조회 시각과 연결 상태를 함께 표시하며 실패하면 같은 프로필의 마지막 정상값을 ‘이전 정상값’으로 구분한다. 다른 프로필이나 모드로 바꾸면 값을 초기화한다. 개발 모드의 숫자는 ‘모의’라고 표시한다.

설정은 서버 주소·SSH 계정/포트·선택 개인키 경로·known_hosts 경로·HTTPS origin의 기존 6개 필드를 유지한다. 파일 찾아보기, 저장/불러오기와 저장 상태 메시지를 제공한다. 잘못된 포트는 입력 단계와 저장/조회 직전 모두 차단한다. 저장은 짧은 확인만 거치며 연결을 시작하지 않는다. 키 내용/비밀번호·연결 승인 플래그를 JSON에 넣지 않는다.

SSH 조회 오류는 인증/호스트 키/연결 끊김/시간초과·취소에 맞는 안내를 대시보드에 표시한다. raw SSH stderr와 HTTP body를 화면/로그에 노출하지 않는다. 고정 읽기 전용 명령, StrictHostKeyChecking=yes, BatchMode, known_hosts 검증, 사용자 SSH config/포워딩 차단, 25초 제한과 취소는 [2차 계약](PHASE2.md)대로 유지한다. 2차의 반복 승인 체크/문구 절차는 위의 3차 수동 버튼 방식으로 대체한다. 내부 수동 실행 guard는 유지하며 버튼 클릭에서만 허용한다.

## 사용자가 실제 Azure 연결을 시험하는 방법

1. 검증된 **전체** Windows 실행 패키지를 풀고 `RiftAssist.ControlCenter.exe`를 실행한다. Windows OpenSSH Client와 기존 개인키/ssh-agent를 준비한다. Windows 10 실기기 검증은 사용자 측에서 수행한다.
2. **서버·운영 → 설정**에서 실제 DNS/IP·SSH 계정/포트·키 경로(또는 준비된 agent)·신뢰한 별도 경로로 fingerprint를 확인한 known_hosts 파일·HTTPS origin을 입력한다. 저장을 선택하고 예를 누른다. 키 내용이나 관리자 키는 입력하지 않는다.
3. 대상을 **Azure · SSH 읽기 전용**으로 바꾸고 대시보드의 **서버 상태 조회**를 누른다. 이 한 번의 명시적 사용자 요청으로 조회하며 추가 확인창은 없다. 앱 시작/설정 저장·불러오기/모드 전환으로 자동 접속하거나 재접속하지 않는다.
4. 6개 상태 카드와 조회 시각을 확인한다. 호스트 키가 없거나 변경됐으면 신뢰한 경로로 확인하며 검증을 끄거나 known_hosts 항목을 임의로 지워 우회하지 않는다. 인증 실패는 계정·키/agent, 연결 실패는 주소·네트워크·SSH 포트를 점검한다.
5. 고정 명령이 기대하는 `riftassist.service`, 앱 `127.0.0.1:3001/api/health`, HTTPS `/api/health`, procfs·sh/awk/head/df/systemctl/curl의 존재/권한을 실제 서버에서 확인해야 한다. 이 구성은 아직 현장 검증하지 않았다. HTTPS 결과는 서버에서 보낸 GET의 응답이며 외부 사용자 네트워크 도달성을 보증하지 않는다. SSH 인증/health GET은 서버 접속·접근 로그를 남길 수 있다.

이번 코드 작업은 실제 서버에 접속하지 않으며 운영 서버 주소·계정·키·연락처를 추정해 채우지 않는다. 실제 관리자 AI/제보/로그·백업/복원·서비스 변경은 제공하지 않는다. 이를 활성화하려면 별도의 인증·권한·배포/복구 설계와 사용자 승인이 필요하다.
