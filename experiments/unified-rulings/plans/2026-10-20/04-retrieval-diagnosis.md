# 점멸 4장 질문: 실제 실패 원인과 개선 계약

2026-10-20. 사용자 제공 질문에 해당하는 운영 기록2건을 읽기 전용으로 대조했다. 다른 이용자의 본문은 결과물에 복사하지 않았다. 새 질문/API 호출/서비스 재시작은 하지 않았다. 기존 검색 함수만 분리해 현재 저장 색인에서 순위를 계산했으며 새 검색 구현의 정확도 검사는 아니다.

## 1. 사실 확인

질문: 상대의 폐기장에 점멸3장이 있는 상태에서 패에서 네 번째 점멸을 사용했다. 어떻게 대처해야 하는가?

공식 코어룰 **103.3.b**는 로컬 색인에도 존재하며, 공식 PDF 원문도 확인했다.

> Your Main Deck can include up to 3 copies of the same named card.

저장된 공식 한국어: 주 덱에는 같은 이름의 카드를 3장까지 포함할 수 있습니다. [공식 코어룰, PDF 3쪽](https://cmsassets.rgpub.io/sanity/files/dsfx7636/news_live/5c7946f7c3b8c6e0faff85ab6dadc6d2e721ea94.pdf#page=3)

| 실제 기록 | 최초 질문 | 같은 카드3장 제한을 명시한 재질문 |
|---|---|---|
| 처리 시각(KST) | 2026-10-20 08:52:32 | 2026-10-20 08:55:59 |
| 요청 ID | 55f5c8a5-8fcb-418b-939a-98d03c47b113 | 8760e4dd-b064-4e2f-acf6-4985dfc7a8bb |
| 당시 AI 입력의 103.3.b | 없음 | 없음 |
| 동일 검색 함수로 계산한 전체 후보 순위 | 1,828위, 점수2.254 | 143위, 점수19.954 |
| 결과 | 근거 부족, 규칙 인용0 | 근거 부족, 대회204.4만 인용 |
| 관련 없는 사례 | 8083: 체인 처리 관련 | 5913/1507/4274: 덱리스트 수집·열람/언어 관련 후보 |

순위는 질문 본문만으로 현 검색을 다시 계산한 진단값이다. 당시 기록에 전체 후보 순위가 저장된 것은 아니다. 당시 최종8개 근거에 해당 조항이 없다는 사실은 저장 기록으로 확인했다. 카드 본문을 합친 두 번째 검색까지 합친 결과도 103.3.b를 포함하지 않았다.

최초 질문의 최종 근거 ID: core366.1 / tournament702.11 / tournament704.4.a.5 / tournament422.4 / tournament509.7 / tournament505.2.a.2 / core358.3.a / core355.11.b.1.

재질문: tournament702.12.b.3 / tournament204.4 / core432.2.b / core366.1 / tournament401.5.a / tournament702.11 / tournament509.7 / core358.3.a.

## 2. 왜 실패했는가

### A. 수량 관계를 읽지 않는 검색

현재 BM25는 표면 단어를 찾는다. ‘폐기장에3장 + 패에서 별도1장’이 같은 이름의 덱 제한 문제라는 연결이 없다. 혼자 있는 한 자리 숫자는 토큰에서 버려지고, ‘3장’ 같은 표현도 복사 수 제한이라는 의미로 해석하지 않는다.

한국어를 2글자 조각으로 잘라 ‘습니/니다/대의’까지 점수에 반영한다. 최초 질문에서103.3.b와 일치한 검색어는 **습니, 니다**뿐이었다. 재질문은 deck/카드/같은 등이 추가되지만 짧은 기본 규칙보다 폐기장·상대·대회가 많이 언급된 문단이 앞섰다.

### B. 기본 규칙과 상황을 연결하는 단계 부재

`TERM_GROUPS`에는 deck 같은 일반 동의어만 있고, same named card / copies / deck construction / 장수 제한의 연결이 없다. 대회 단어가 있으면 대회 문단을 우선하지만 그 문단이 위반 유형과 관련 있는지 확인하지 않는다.

### C. 카드 효과가 쟁점을 덮음

선택된 점멸의 영어 효과 전체를 추가 검색어로 쓴다. 이 질문에 필요한 것은 카드의 동일 이름과 장수인데, 이동/리액션/유닛 정보가 검색을 다른 방향으로 끌었다. 첫 검색은 이미8개로 잘린 상태이고, 첫6개와 카드 검색 결과를 합쳐 다시8개를 고른다. 후보 전체를 쟁점별로 재정렬하지 않는다.

### D. 근거에 없으면 모델은 답할 수 없도록 설계됨

모델은 제공된 공식 근거만 사용하도록 제한되어 있다. 모델에게103.3.b가 전달되지 않았고, 서버는 규칙 인용0일 때 추천 문구를 ‘신뢰할 수 있는 판정을 뒷받침하기 어렵다’로 덮어쓴다. 이 방어 자체를 제거해서 기억에 의존하게 만드는 해결책은 적절하지 않다. **검색 누락을 먼저 고쳐야 한다.**

### E. 공통 불확실성을 전체 결론에 적용

카드가 community-source라는 이유만으로 답변 전체의 신뢰도를 낮추고 저지 확인 필요를 켠다. 점멸 효과의 검증 여부와 공식 덱 구성 제한의 존재는 다른 문제인데, 답변은 팬 사이트·공식 카드 문구 부재를 장황하게 설명했다. 재질문에서 이미 ‘공식 대회’라고 적었는데도 같은 내용을 다시 물었다.

### 추가로 발견한 취약점

- 사용자 표기 `103.3b`와 저장 ID `103.3.b`를 정규화하지 않는다. 명시적 조항을 적어도 우선 검색이 어긋날 수 있다.
- **원문 추출 과정에서 조항을 덮어쓰는 결함도 확인했다.** 로컬 공식 대회 PDF(표지 개정일2026-10-09)의43·45쪽을 텍스트 추출과 이미지로 대조했다.43쪽의703.4.a.5는 덱 박스에 등록되지 않은 카드가 있는 경우와 예외를 설명한다.45쪽의703.4.c.5는 그 번호를 참조하며 Professional OPL의 처분 조건을 설명한다. 그런데 줄바꿈 뒤의 참조 번호를 새 조항 시작으로 인식하고 `rules.set(current.id, ...)`가 이전 값을 덮어쓴다. 결과적으로 현재 색인의a.5는 처분 승격 문장 끝만, c.5는 참조 번호 앞부분만 남았다. 페이지 링크도 원래43쪽에서45쪽으로 바뀌었다. 이 결함은103.3.b 누락의 직접 원인과 별개지만, 자동 갱신 전에 해결할 사항이다.
- 최종 선택 목록만 기록되어 ‘왜 필요한 조항을 제외했는지’가 보이지 않는다. 후보 순위/의도/예외 검사 기록을 추가해야 한다.

## 3. 이 질문의 목표 답안 초안

> 일반적인 덱 구성 제한이 적용되는 게임이고, 폐기장의 점멸3장과 지금 사용한 점멸이 모두 상대의 원래 덱에 들어 있던 서로 다른 카드라면, 같은 이름 카드의 장수 제한 위반을 의심할 수 있습니다. 코어룰103.3.b는 같은 이름의 카드를 주 덱에 최대3장까지 허용합니다.
>
> 대회 중이라면 상대에게 확인을 요청하고 저지를 불러 현재 카드와 게임 상태를 보여 주세요. 플레이어끼리 그 주문을 무효로 하거나 카드를 임의로 빼서 해결하지 말고, 저지가 덱/등록 목록과 발생 경위를 확인하도록 하는 것이 적절합니다.
>
> 다만 ‘이번 게임에서 네 번째로 사용했다’는 횟수만으로는 위반을 확정할 수 없습니다. 같은 카드를 다시 사용했는지, 다른 출처의 카드인지, 적용 포맷의 별도 구성 규칙이 있는지를 구분해야 합니다. 구체적 처분은 그 확인 결과에 따라 달라집니다.

검수용 초안이며 저지 승인 정답이 아니다. 같은 이름/선택 챔피언/포맷 적용은 코어103.3.b와 하위·주변 조항을 함께 확인한다. 대회에서는 저장된403.3(주 덱·사이드보드 합산),703.3(덱 목록 오류),703.4(제시된 덱 오류),703.4.e(상대 덱 적법성 확인 요청) 관련 맥락을 함께 검색해야 한다. [대회 원문 PDF](https://cmsassets.rgpub.io/sanity/files/dsfx7636/news_live/861752822d217edf37d9febaeaf77a7d924c1bb6.pdf#page=42)

이번 웹 도구는 대회 PDF의 크기 때문에 본문을 열지 못했으나, 저장된 공식2026-10-09 PDF43·45쪽을 직접 읽고 시각 확인했다.703.4.e의 덱 적법성 확인 요청과 위 추출 결함을 확인했다. 구체적 처분·상향 조건은 최신 정오표와 사건 사실까지 대조하고 저지 검수 후에 확정한다. AI가 ‘네 장 = 실격/부정행위/즉시 게임 패배’로 단정하게 만들지 않는다.

### 원문 파서 수정 준비

- 조항 번호 열과 본문 열을 PDF 좌표/행 구조로 구분한다. 본문에서 줄 첫머리로 밀린 참조 번호를 새 정의로 보지 않는다.
- 같은 문서/버전에서 같은 ID가 두 번 정의되면 조용히 덮어쓰지 말고 두 위치와 원문을 보존하며 검증 실패로 처리한다. 단순히 첫 값만 보존하는 처리도 누락을 숨기므로 쓰지 않는다.
- 표/문단, 페이지 넘어가는 문장, 제목과 하위 조항, 참조 링크를 함께 보존한다. 문서 레이아웃 변경 시 자동 적용을 보류한다.
- 703.4.a.5와703.4.c.5를 추출 회귀 확인 항목으로 지정한다. ‘규칙 번호가 존재한다/항목 개수가 비슷하다’만으로 통과시키지 않는다.
- 기존 색인의 전체 오류 규모는 아직 조사하지 않았다. 파서 개선 후 새 임시 색인과 기존본의 차이를 확인하며, 현재 배포 색인을 바로 덮어쓰지 않는다.

## 4. 개선 파이프라인

1. **사실 추출(기본은 코드)**: 카드 canonicalNameId, 수량, 영역, 소유/출처, 시간(동시에 존재/누적 사용), 사건, 대회 명시 여부를 분리한다. 한국어 수사/영어를 지원한다. ‘폐기장3 + 패의 다른1’과 ‘총4회 사용’을 다른 구조로 만든다.
2. **쟁점 태그(여러 개 가능)**: deck-construction, card-effect, timing, targeting, cost, ownership, event-remedy 등. 점멸이라는 특정 카드명이 아닌 수량 관계로 deck-construction을 활성화한다. 명시 사실과 추정 태그를 구분한다.
3. **기본 규칙 묶음 검색**: 쟁점→규칙 연결표에서 덱 구성/장수/동일 이름/선택 챔피언/포맷 적용을 후보에 올린다. 조항 번호는 정규화하고 정확 ID 조회를 먼저 한다. 연결표는 해당 자료 버전에 묶고 새 문서에서 사라진 조항은 자동 추정 연결하지 않는다.
4. **상황·효과 검색**: 질문 쟁점에 카드 효과가 필요할 때만 효과 본문을 확장어에 넣는다. 불필요한 유닛 이동 문구가 덱 제한 후보를 밀어내지 않게 한다.
5. **넓게 후보 수집 후 좁히기**: 유형별 후보를 합쳐 최대40개 내부 검토, 중복·무관어 제거·부모 조건·예외를 기준으로 다시 정렬한다. 문서 빈도는 자료 빌드 때 계산한다. 후보40개 전체를 AI에 보내지 않는다.
6. **근거 커버리지 검사**: 핵심 원칙/예외/요청한 처리 절차가 포함됐는지 확인한다. 최종 예산은 현재처럼 최대8개 근거 묶음·사례 최대4개를 기본으로 유지한다. 예시 배분은 기본2/직접 상황3/대회 처리2/예외1이지만 관련 없는 자리를 강제로 채우지 않는다. 묶음은 조건과 필요한 하위 조항만 포함하며 본문 크기를 제한한다.
7. **RiftJudge 검색**: 같은 카드명보다 같은 쟁점·조건을 우선한다. 해당 질문이면 deck construction / same named card / copies / deck legality 의미를 보존한다. 사례 상태와 당시 규칙 버전, 일치점·차이점을 기록한다. 사례가 없더라도 공식 규칙으로 답할 수 있으면 답한다.
8. **생성과 후처리**: 기본 원칙 → 현재 사실 → 조건부 결론 → 대회 조치 순서. 인용된 ID뿐 아니라 결론에 필요한 조건이 입력 근거에 있었는지 확인한다. 부족한 부분만 확인 질문으로 남긴다.

상위 모델/전체 규칙 매번 전송/모델 재학습은 초기 해결책에 포함하지 않는다. 먼저 검색을 고치고 사람 승인 문항으로 누락률을 확인한다. 그래도 표현 차이로 실패하는 질문에만 작은 검색어 재작성1회나 하이브리드 검색을 검토하며 기본 경로는 추가 AI 호출0회다.

## 5. 기록할 최소 정보

requestId, app/prompt/search/data 버전, 추출 사실과 근거 위치, 쟁점 태그, 최종 검색어, 후보 ID/점수/선정·제외 사유, 핵심 근거 포함 여부, 사례 연결 이유, 실제 인용 ID, 입력/출력/캐시/추론 토큰, 오류 종류. **모델의 비공개 사고 과정은 수집하지 않는다.**

관리 화면의 제보 상세에서 ‘검색 누락 / 원문 파싱 / 버전 충돌 / 생성 오류 / UI 표시’로 나눠 분석 가능하게 한다. 원래 질문이 보존 만료됐을 때 이를 오래된 진단 파일로 우회 보관하지 않는다.
