# v0.2.0 배포·롤백 계획 — 실행하지 않음

현재 운영 서버 수정·재시작, Azure 작업, GitHub push/merge, 공유 DB/키/활성 자료 포인터 변경은 승인 범위 밖이다. 아래는 향후 별도 승인을 위한 절차이며 자동화된 배포 기능을 추가하지 않았다.

## 승인 전

1. v0.1.7 프로세스와 기존 데이터 루트를 유지한다. v0.2.0은 `.dev-data/` 또는 별도 마커가 있는 새 루트, 다른 포트·도메인에서만 실행한다. 기존 `private/`, 키, 카드 원본·백업, `knowledge-releases/active.json`을 복사하거나 덮어쓰지 않는다.
2. 개발은 합성 카드와 고정 규칙 fixture·모의 응답으로 수행한다. 이 자료를 공식 API 데이터나 라이선스 증거로 제출하지 않는다. 심사 설명에는 합성/미승인/실제 공식 자료의 차이와 남은 연동 작업을 밝힌다.
3. 운영자·권리 요청 연락처, 처리 근거·동의 필요 여부/실제 방식, 외부 계약·국외 이전, 로그·백업 삭제 절차를 확정한다. 현재 입력 템플릿의 null은 동의·승인을 의미하지 않는다.
4. Git 런타임 DB 추적 제외와 배포 패키지 검사를 완료한다. 기존 데이터/DB·키를 이미지나 소스 패키지에 포함하지 않는다. 공개 배포 전 자료 사용 범위와 참고형 AI 기능의 정책 수용 여부를 Riot에 확인한다.

## Riot 승인 후, 운영 전환 전

1. 승인된 앱과 API 권한 범위·조건을 문서로 확인한다. 승인 앱 참조, 실제 endpoint·응답 스키마·페이지네이션·rate limit·정오표·언어·미출시 표시 계약을 확인한다. 현재 예시 canonical 형식은 Riot 응답 명세가 아니다.
2. 승인된 호스트에만 통신하는 실제 `decodeOfficial` 매퍼를 구현하고 고정 공식 샘플을 비식별 fixture로 검증한다. 키는 배포 환경의 비밀 저장소/환경 변수로 주입한다. Git·JSON 설정·이미지·로그에 넣지 않는다. 키 존재나 승인 이벤트가 수집/배포를 자동 실행하게 하지 않는다.
3. 별도 staging 루트에 실제 공식 데이터 **후보**를 수집한다. import preview와 버전/해시를 검증하고, 영문 원문·공식 한국어 존재 여부·번역 권한/정확성·이미지 출처·미출시 표시·중복 ID·필수 필드를 점검한다. 미승인 RiftNaru 자료를 보완값으로 섞지 않는다.
4. 후보의 카드별 display/modelInput 권한을 검토한다. 실제 API로 받았다는 이유만으로 모든 재사용·모델 전송 권한이 있다고 가정하지 않는다. 권한 검토 후에도 `verified-only`를 명시적으로 선택해야 표시된다. mock 자료는 staging/production 뷰에서 거절된다.
5. 별도 staging의 새 운영 DB·새 암호화/세션/관리자 키로 카드 검색·AI·번역·제보·관리·삭제 주기와 장애 처리를 검증한다. 유료 외부 호출은 별도 허용 범위를 먼저 정해야 하며 현재 작업에서는 모두 모킹했다.
6. 공개 HTTPS, 인증/헤더, 실제 브라우저·PWA 갱신/오프라인·캐시 롤백, 부하·rate limit·장애 대응을 점검한다. 자동 수집과 지식 게시를 허용하려면 새 공식 경로에 한정해 별도 검토한다. 기존 수집기 자동 실행은 비활성이다.
7. 최종 코드·자료 해시와 검증 결과, 위험·연락처·운영 절차가 정해진 후에만 릴리스 ready 표시를 검토한다. **사용자의 배포 승인**은 별도 최종 단계다. Git push/merge와 Azure 변경도 별도 승인 전에는 하지 않는다.

## 승인된 전환의 원칙

- 기존 v0.1.7 관리자·앱은 종료하지 않은 채, v0.2.0을 독립 프로세스·루트·키로 병렬 준비한다. 현재 루트 릴리스 manifest는 ready=false이므로 운영 전환 후보로 자동 선택하지 않는다.
- 가능하면 v0.2.0은 별도 origin에서 검증한다. 동일 origin으로 최종 전환한다면 서비스 워커·HTML 캐시·열려 있는 탭의 갱신과 되돌림을 실제 환경에서 먼저 검증해야 한다. 이미 제공한 카드 이미지/메모리/외부 전송을 소급 회수할 수 없다.
- 트래픽 라우팅 변경은 사용자가 승인한 유지보수 절차에서 수행한다. v0.1.7의 `knowledge-releases/active.json`이나 DB를 v0.2.0으로 교체하는 방식으로 전환하지 않는다. 어떤 기존 Dockerfile을 그대로 운영 패키지라고 가정하지 않는다.
- 두 버전의 DB는 호환되는 기본 스키마를 유지하지만 공유해서 쓰지 않는다. v0.2.0의 새 제보는 새 DB에 남고 기존 제보/사용자 기록은 v0.1.7에 남는다. 기록 이관이 필요하다면 별도의 읽기 전용 원본·검증·승인을 포함하는 계획부터 수립한다.
- 사용자·관리자 쿠키 이름도 버전별로 다르므로 v0.2.0 쿠키 발급이 v0.1.7 서명 쿠키를 덮어쓰지 않는다. 기존 브라우저의 계정/제보 접근 상태와 실제 도메인 쿠키 조건은 staging에서 검증한다.

## 실패 시 롤백

1. 전환 실패/오류율·카드 누출·인증 장애 등의 기준을 사전에 정한다. 이상 시 v0.2.0으로 신규 유입만 차단하고 승인된 라우팅을 기존 v0.1.7로 되돌린다. 진행 중 요청의 처리·유료 호출 중복 방지는 배출/상태 확인 후 수행한다.
2. v0.1.7의 원본 프로세스·DB·키·지식 포인터를 그대로 사용한다. v0.2.0 SQLite 파일을 원본 위에 복원하거나 암호화 키를 맞바꾸지 않는다. 역방향 DB 마이그레이션도 실행하지 않는다.
3. v0.2.0의 로그·새 제보는 별도 데이터 루트에서 보존하고 개인정보 보관/삭제 정책에 따라 처리한다. 롤백이라는 이유로 사용자 기록이나 개발·운영 자료를 삭제하지 않는다.
4. 동일 origin 전환이었다면 PWA·정적 캐시의 v0.1.7 화면 복귀까지 확인한다. 서버 라우팅만 되돌렸다고 모든 열린 창이 즉시 이전 UI로 바뀐다고 보장하지 않는다.
5. 기존 버전이 정상 응답하는 것을 확인한 후 실패 후보를 분석한다. 원본 DB·백업 복원은 이번 무변경 롤백 설계에 필요하지 않다. 실제 복원이 필요한 별도 사고는 같은 키/DB의 검증된 백업과 독립 승인이 필요한 다른 절차다.
